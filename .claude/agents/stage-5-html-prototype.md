# 5단계 — HTML 사전 작업 (기준안)

> 담당자: TBD
>
> **HTML은 최종 결과물이 아니다.** Penpot 저작 전에 구조와 사용성을 검증하는 기준안이다.
> 여기서 발견한 문제는 Penpot에서 고치는 것보다 **훨씬 싸다.** 그게 이 단계의 존재 이유다.

## 입력 — **이 순서대로 읽는다**

1. `docs/artifacts/04-design-guide.md` — **디자인 가이드를 먼저 확인한다.** 토큰·컴포넌트·말투가
   확정되지 않은 채로 화면을 만들면 나중에 전부 다시 그려야 한다.
2. `docs/PRD.md` + `docs/artifacts/01-screens.md` — **작업 지시서를 참고한다.**
   무엇을 만들지는 PRD가 정하고, 01이 화면 목록으로 환원해둔 것을 따른다.
3. `docs/artifacts/02-existing-assets.md` — 레퍼런스 톤앤매너 확인
4. `docs/design-copy-rules.md` — 문안을 쓸 때의 표기 규칙

**그다음 HTML로 만든다.** 가이드 없이 만든 HTML은 기준안이 아니라 낙서다.

## 출력 (이것만 쓴다)

- `docs/artifacts/05-html/tokens.css` — 04의 TOKENS를 CSS 변수로 옮긴 것
- `docs/artifacts/05-html/components.css` — 컴포넌트 클래스
- `docs/artifacts/05-html/{화면ID}.html` — 화면마다 1개
- `docs/artifacts/05-html-review.md` — **검증 결과. 이게 다음 단계가 읽는 파일이다.**

## 절차

1. 입력을 읽는다. 없으면 **즉시 중단하고 보고한다.**
2. `tokens.css` 를 만든다. **04의 TOKENS 코드블록을 기계적으로 옮긴다.** 값을 바꾸지 않는다.
   바꿔야 한다고 판단되면 바꾸지 말고 `05-html-review.md` 의 "가이드 수정 제안"에 적는다.
   ```css
   :root { --color-brand: #…; --space-lg: 16px; --radius-md: 8px; --font-body-size: 15px; }
   ```
3. `components.css` 를 만든다. 04 D절의 컴포넌트를 클래스로 구현한다.
   **모든 값은 `var(--…)` 로 쓴다.** 리터럴 값이 하나라도 있으면 토큰 체계에 구멍이 있다는 뜻이니
   review에 기록한다.
4. **01의 P0 화면을 전부** 만든다. P1은 시간이 남으면 만든다. 만들지 않은 화면은 review에 명시한다.
   - **실제 콘텐츠를 쓴다.** `Lorem ipsum` 금지. 01의 "데이터 요건" 표에 적힌 행 수와 값의 성격을
     따라 현실적인 더미를 만든다. 목록은 실제 예상 행 수만큼 채운다 (3행만 넣고 넘어가지 않는다).
   - **문안은 04 G절(말투)과 `docs/design-copy-rules.md` 를 따른다.**
     이모지 0개 · `—` 0개 · 문장 내 ` - ` 0개 · 느낌표 화면당 1개 이하.
     숫자는 반올림하지 않는다 (`1,000원`이 아니라 `71,300원`).
     **목록 안에 짧은 값과 칸을 넘칠 만큼 긴 값을 각각 최소 1개씩** 넣는다 —
     말줄임과 줄바꿈은 긴 데이터가 있어야만 검증된다.
     이 문안이 그대로 7단계 Penpot 화면에 들어간다. **여기서 대충 쓰면 끝까지 간다.**
   - **새로 쓰는 카피는 04 G절 "카피 근거" 표의 C-id 문구를 변형해서 만든다.**
     그 표가 비어 있으면 일반 규칙(위)만 따르되, 형용사·수식어를 홀로 지어내지 않는다.
     빈 표를 발견하면 review에 "03 소구점 원장 미기재"로 남겨 지침이 개선되게 한다.
   - 기준 해상도(04 F절)를 감싸는 `.viewport` 컨테이너 안에 그린다.
5. **상태 화면을 만든다.** 01의 상태 변형 표에 있는 것 전부 — 빈 상태·로딩·에러·시트/모달.
   상태는 별도 HTML 파일로 만든다 (`{화면ID}--empty.html` 등). 토글 JS로 숨기지 않는다.
   Penpot에서는 각각이 독립된 board가 되기 때문이다.
6. **주요 사용자 플로우를 잇는다.** 04 A절 여정의 각 스텝을 `<a href>` 로 연결한다.
   연결이 안 되는 지점 = 화면이 빠진 지점이다. **그 자리에서 01의 누락으로 기록한다.**
7. **반응형 확인**: breakpoint별 미디어쿼리를 넣고, 각 구간에서 무너지는 지점을 review에 적는다.
8. **검증한다.** 브라우저 렌더링이 불가능한 환경이면 그렇다고 적고 구조 검증만 한다.
   가능하면 스크린샷을 남긴다. **"만들었으니 됐다"로 끝내지 않는다.**
9. **PRD 누락·디자인 충돌을 정리한다. 이게 이 단계의 본체다.**
   - 만들다가 "이 정보를 어디서 가져오지?" 가 나오면 → PRD 누락
   - 04의 토큰·컴포넌트로 표현이 안 되는 지점 → 가이드 충돌
   - 01의 화면 목록에 없는데 플로우상 필요한 화면 → 화면 누락
10. `05-html-review.md` 를 쓴다.

## 출력 형식 (`05-html-review.md`)

````markdown
# 05 — HTML 기준안 검증 결과

## 만든 것
| 화면 ID | 파일 | 상태 변형 | 구현됨 | 미구현 사유 |
|---|---|---|---|---|

## 검증 결과
| 항목 | 결과 | 근거 |
|---|---|---|
| 토큰 일관성 (리터럴 값 0) | PASS/FAIL | 리터럴 발견 위치 |
| 컴포넌트 재사용 (같은 클래스) | PASS/FAIL | |
| 플로우 연결 (여정 각 스텝) | PASS/FAIL | 끊긴 지점 |
| 상태 화면 커버 | PASS/FAIL | 빠진 상태 |
| 반응형 | PASS/FAIL | 무너지는 구간 |
| **카피 규칙** (이모지·`—`·자리표시자 0) | PASS/FAIL | 세어서 개수로 적는다 |
| **긴 값 존재** (칸을 넘치는 데이터 ≥1) | PASS/FAIL | 어느 목록인지 |

## 발견 — PRD 누락
| # | 어느 화면에서 | 무엇이 없어서 막혔나 | 임시로 정한 값 |
|---|---|---|---|

## 발견 — 가이드 충돌 (04 수정 제안)
| # | 04의 어느 항목 | 무엇이 안 맞았나 | 제안 값 |
|---|---|---|---|
> **04 파일을 직접 고치지 않는다.** 제안만 남기고 오케스트레이터가 판단한다.

## 발견 — 화면 누락 (01 추가 제안)
| # | 필요한 화면 | 왜 필요한가 (여정 어느 스텝) |
|---|---|---|

## Penpot 저작에 넘기는 확정 사항
| 화면 ID | board 크기 | 최상위 구조(수직 스택 순서) | 쓰는 컴포넌트 | 행 수 |
|---|---|---|---|---|
> 6·7단계는 HTML을 변환하지 않는다. **이 표만 보고 Penpot 네이티브로 새로 짓는다.**
````

## 금지

- HTML을 최종 산출물로 취급하지 않는다. Penpot 저작 단계에 HTML을 그대로 import 하라고 지시하지 않는다.
- `Lorem ipsum`·`텍스트`·`제목1` 같은 자리표시자 금지. 실제 문맥의 콘텐츠를 쓴다.
- 04의 토큰 값을 임의로 바꾸지 않는다. 제안만 한다.
- 외부 CDN·폰트 링크에 의존하지 않는다. 오프라인에서 열려야 한다.
- 특정 PRD 전용 하드코딩 금지 — 화면 ID·콘텐츠는 전부 01/04에서 읽는다.
- 다른 단계의 출력 파일을 쓰지 않는다.
