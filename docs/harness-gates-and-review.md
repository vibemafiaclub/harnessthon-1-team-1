# 단계 게이트·전문가 리뷰 정본 (Penpot 접점 2곳 원칙 포함)

> ⚠️ **구조 매핑 노트 (2026-08-01)**: 이 문서는 구 7단계 구성안 기준으로 작성됐다.
> 현행 8단계 구조 매핑 — 구1 도메인리서치→stage-3·4에 분산 / 구2 페르소나→stage-4 /
> 구3 경쟁사→stage-3 / 구4 유저플로우·화면 인벤토리→stage-1 / 구5a 토큰실측→stage-2 /
> 구5b·6 저작→stage-6·7 / 구7 verify→stage-verify-penpot.
> 원칙(R1~R8 런타임 규칙·GATE 게이트·Penpot 접점 2곳·소구점 원장)은 구조와 무관하게 유효하다.


> 짝 문서: `harness-failure-modes.md`(실패 대응) — 이 문서는 **정상 진행의 관문**을 정의한다.
> "각 단계가 끝났다고 어떻게 확신하고 다음으로 넘어가는가"의 답.

## 1. Penpot 접점 2곳 원칙

Penpot MCP는 파이프라인에서 **딱 두 접점**에서만 쓴다. 나머지는 전부 md 파일 작업이다.

```
        [접점 A: 읽기]                                    [접점 B: 쓰기]
  Penpot 기존파일 → 05a 실측                       05b 컴포넌트 + 06 저작 → Penpot
        │                                                 ▲
        ▼                                                 │
  ┌─────────────── md 전용 구간 (Penpot 안 건드림) ────────┐
  │  01 리서치 → 02 페르소나 → 04 유저플로우              │
  │  03 경쟁사 ↗                                          │
  └───────────────────────────────────────────────────────┘
  (07 verify는 접점 B의 검수용 재읽기 — 읽기 전용)
```

**왜 이 구조인가:**
- **팀 분업**: md 전용 구간(01~04)은 Penpot 연결 없이 각자 로컬에서 고도화·테스트 가능.
  MCP 셋업(플러그인 탭 유지)이 필요한 사람은 5a·5b·6·7 담당자뿐이다.
- **리스크 격리**: 가장 위험한 변수(MCP 끊김)가 파이프라인 앞뒤로만 몰린다.
  중간에 끊겨도 md 산출물은 전부 살아 있어 접점 B부터 재개하면 된다.
- **재현성**: 심사 때 md 구간은 어떤 환경에서도 동일하게 돌아간다.

**규칙**: 01~04 단계 agent 본문에는 Penpot 도구 사용 자체를 금지한다고 명시한다.
읽을 게 필요하면 `05a-tokens.md`(접점 A의 산출물)를 읽지, Penpot을 직접 읽지 않는다.

## 2. 단계 게이트 — "다음으로 넘어가도 되는가"의 기계적 판정

모든 산출물 md는 맨 끝에 `## GATE` 절을 갖는다. 아래 표의 조건을 스스로 체크해
`PASS / PARTIAL / FAIL`을 선언한다. **start 오케스트레이터는 다음 단계를 호출하기 전에
앞 산출물의 GATE 절만 읽고 판정한다** (본문 재해석 금지 — 게이트가 곧 계약).

| 게이트 | 다음 단계 진행 조건 (전부 충족 = PASS) |
|---|---|
| **G1** (01-research) | 최근 1년 내 소스 3건 이상(발행일 기록) · 소구점 "불편→약속" 쌍 5개 이상(verbatim+출처) · 폴백 사용 시 첫 줄 명시 |
| **G2** (02-persona) | 페르소나 2~3명 · 모든 필드에 근거 출처 또는 `근거 부족` 표기 · 유저 스토리 커버리지 맵에 미커버 스토리 0 |
| **G3** (03-competitors) | 앱 3~5개+선정 지표(또는 프록시) 기록 · 과업→화면 시퀀스가 핵심 유저 스토리 수 이상 · 앱당 소구점 verbatim 3개 이상 · 사용한 화면 소스 기록 |
| **G4** (04-userflow) | 환원 규칙 4종 체크리스트 전 행 처리 · P0에 PRD 명시 필수 화면 전부 포함 · 모든 화면에 근거 문장+포지션 반영+주 페르소나 컬럼 채움 |
| **G5a** (05a-tokens) | 시멘틱 토큰 구조 완비(색 main/light/dark/contrastText·타이포 variant·spacing 스케일) · 폰트 가용성 확인 기록 · 실측 출처 Page 이름 기록 |
| **G5b** (05b-components) | `04` 화면 인벤토리의 필요 컴포넌트 100% 매핑(제작 or 미제작 사유) · 각 컴포넌트 Penpot 노드 id 기록 · P0 사용 컴포넌트는 상태 3종 존재 |
| **G6** (06-author) | P0 화면 전부 PNG export 존재 · 화면별 검수 체크(텍스트 잘림·스크림·좌표) 기록 · 모든 문구에 소구점 참조 id |
| **G7** (99-verify) | `04` 화면 목록 × Penpot board 1:1 대조표 · PARTIAL 존재 시 완료 선언 금지 |

**판정별 동작** (failure-modes R3·R5와 일관):
- `PASS` → 다음 단계 호출
- `PARTIAL` → 다음 단계를 **저신뢰 모드로 진행**시키되(있는 것만 사용), 런로그에 기록.
  단 G4·G5b의 PARTIAL은 저작 품질에 직결되므로 P0 범위만으로 축소 진행
- `FAIL` → 해당 단계 1회 재실행. 재실행 후에도 FAIL이면 그 브랜치만 멈추고 병렬 형제는 계속

## 3. 전문가 피드백을 하네스 안에서 주는 방법

무인 실행이므로 사람 리뷰를 기다릴 수 없다. 피드백은 **두 겹**으로 자동화한다.

### 3-1. 소비자 검증 (기본, 추가 비용 0)

**다음 단계 agent가 곧 앞 단계의 검수자다.** 각 agent는 작업 시작 전에 입력 산출물을
"내가 이걸로 일할 수 있는가" 관점으로 검사하고, 문제를 발견하면
`docs/artifacts/feedback/{NN}-feedback.md`에 기록한다.

```markdown
# feedback: 03-competitors → 04-userflow
- [BLOCK] 과업→화면 시퀀스가 목록 나열임. 시퀀스 없이는 플로우 설계 불가
- [WARN] 앱 2개만 수집됨(기준 3~5). 있는 것으로 진행, 신뢰도 하향 표기
```

- `BLOCK` = 앞 단계 1회 재실행 요청 (feedback 파일을 재실행 입력으로 전달 — 전면 재작업이
  아니라 지적 항목만 국소 보수)
- `WARN` = 자기 단계에서 보정하고 진행. 기록만 남긴다

### 3-2. 전문가 렌즈 자체 검수 (게이트에 내장)

각 단계 agent는 GATE 선언 직전에 **그 단계 전문가의 킬러 질문**으로 자기 산출물을 1회
적대 검수한다. 렌즈 질문은 agent 본문에 박는다:

| 단계 | 렌즈 | 킬러 질문 |
|---|---|---|
| 01 | UX 리서처 | "이 데이터 중 디자인 결정을 실제로 바꾸는 것은 몇 개인가? 장식용 데이터는 삭제했는가?" |
| 02 | NN/g 리서처 | "이 페르소나 둘의 차이가 화면 설계를 다르게 만드는가? 안 만들면 1명으로 합쳐라" |
| 03 | 프로덕트 디자이너 | "이 플로우만 보고 화면을 그릴 수 있는가? 화면 사이 전환 트리거가 다 있는가?" |
| 04 | IA | "이 화면을 지우면 어떤 유저 스토리가 끊기는가? 답 못하는 화면은 P2로 강등하라" |
| 05a | 디자인 시스템 엔지니어 | "이 토큰만 주고 다른 사람이 같은 톤의 화면을 만들 수 있는가? 값에 예외가 몇 개인가?" |
| 05b | 컴포넌트 설계자 | "06이 이 컴포넌트 인스턴스만으로 P0 화면을 조립할 수 있는가? 빠진 조각은 무엇인가?" |
| 06 | 시니어 디자이너 | "이 PNG를 실서비스 스크린샷이라고 우길 수 있는가? 어긋난 정렬 하나를 찾아라" |
| 07 | QA | "PASS 판정에 서술이 섞였는가? 표의 행 수가 04의 화면 수와 같은가?" |

킬러 질문에서 걸린 것은 즉시 자기 산출물을 고치고 GATE를 선언한다 (별도 라운드 없음 —
시간 예산 안에서 끝내기 위해 검수·수정은 같은 agent 호출 안에서 1회전만).

### 3-3. 사람 리뷰 접점 (무인 실행 밖)

무인 런이 끝나면 팀원은 이 순서로만 보면 된다 (전부 md라 Penpot 없이 리뷰 가능):
`00-runlog.md`(무슨 일이 있었나) → `feedback/`(에이전트끼리 주고받은 지적) →
각 산출물의 `## GATE` 절(뭐가 PARTIAL인가) → PNG(최종 결과물).
사람 피드백은 feedback 파일과 같은 형식(BLOCK/WARN)으로 적으면 다음 런의 입력이 된다.

## 4. scaffold 시 반영 방법

- 각 stage agent 템플릿의 "절차" 마지막 2줄을 고정한다:
  `n-1. 전문가 렌즈 킬러 질문으로 자체 검수 → 걸린 것 수정` /
  `n. 산출물 끝에 ## GATE 절 작성(PASS/PARTIAL/FAIL + 근거)`
- start 오케스트레이터의 단계 호출 규칙에 추가:
  "다음 단계 호출 전 앞 산출물 GATE 절 판정 → PASS/PARTIAL/FAIL 분기(§2)"
- 01~04 agent에는 "Penpot 도구 사용 금지(접점 2곳 원칙)" 1줄을 넣는다.
